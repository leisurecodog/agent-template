# 判斷力 Rubric

用途：把原本靠模型直覺的判斷，變成任何等級的模型都能機械執行的檢查。
每條 rubric 附一個正例（該這樣做）和一個反例（不該這樣做）。
遇到 rubric 蓋不住的情況：升級模型或問使用者，不要自由發揮。

## R1. 何時該升級模型

**判準**（任一成立就升級，路徑見 model-dispatch.md 第 5 節）：
- 已確認該 model 的 effort 調到頂仍不夠（effort-first、tier-second，見 model-dispatch.md §3）。
- 同一驗收條件下已失敗達到 `model-dispatch.md` 第 5 節的升級門檻（門檻數字只在該處維護）。
- 任務需要在多個都「說得通」的方案間做取捨，且選錯的修復成本高（架構、資料 schema、對外介面）。
- 你發現自己在兩個做法之間來回改超過一次——這是能力不足的訊號，不是任務模糊的訊號。

**正例**：中等模型 agent 兩次修同一個測試失敗，第二次的修法把另一個測試弄壞了。
→ 停止，整理兩次的 diff 與測試輸出，升一級。

**反例**：較弱模型改壞一個 import 路徑，主對話讓它「再試一次」，又錯，再試第三次。
→ 錯。較弱模型錯 1 次就該直接升級，三次重試燒掉的 token 比升級貴。

## R2. 何時算真的完成

**判準**（全部成立才算完成）：
- 每一條驗收條件都有**證據**：測試輸出、實跑結果、read-back 內容。「我改好了」不是證據。
- 程式碼改動：至少實跑過一次改動路徑（測試、或手動執行入口），輸出貼在回報裡。
- 檔案產出：read-back 確認落地且內容完整（不是空檔、不是截斷）。
- 使用者的原始要求逐項對照過——不是「主要部分」完成，是每一項。

**正例**：「已完成。驗收：`pytest tests/test_order.py` 3 passed（輸出如下）；
`report.md` read-back 確認含全部 5 個章節。」

**反例**：「已完成下單篩選功能，程式碼寫在 screener.py。」——沒跑過、
沒輸出、沒對照原始要求裡「近三天內剛轉正」的條件是否處理了邊界。這叫寫完，不叫完成。

## R3. 何時該停下來問使用者

在權限幾乎全開的環境，這條 rubric 是主要的安全網。
**遇到以下情況必停**（即使環境鼓勵自動繼續）：

- 動作不可逆且非使用者明示：刪除或整檔覆寫**非本次 session 建立**的檔案（備份也要先做）、
  `git push --force`、rotate 金鑰。用 Edit 局部修改既有檔案不算覆寫；記憶目錄的過時條目
  依 maintenance-protocol.md 第 3 節清理，不必問。
- 對外發送：email、即時通訊訊息、`git push`、發 PR、API 寫入外部服務。
  （例外：使用者在本次對話中已明確授權該次發送。）
- 花費真金白銀或大量配額：長時間高階模型迴圈、大量 API 呼叫。
- 兩個解讀會導向完全不同的產出，且做錯要重來（例如「報告」是指 md 檔還是網頁）。
- 升級鏈到頂仍失敗（見 R1）。

**不必問的**（前提：請求本身已要求實作。只是問問題、要診斷或要計畫時，見 CLAUDE.md
「動手邊界」——那時不動使用者的專案檔案）：工具選擇、檔名、程式內部結構、新建檔案、
用 Edit 局部改碼、跑測試與唯讀指令、寫 scratchpad、可逆的中間步驟——選合理預設，做，
回報時說明。

**正例**：任務是「把摘要寄給我」。→ 草稿寫好後先展示，問「確認寄出？」再寄。

**反例**：不確定使用者要 CSV 還是表格，於是停下來問。→ 錯。兩個都便宜、可重做，
選一個（或都給），一句話說明即可。

## R4. 方向錯了的訊號（該換路，不是再重試）

重試 = 同方法再來一次。換路 = 改變方法。以下訊號出現時，**重試是浪費**：

- 錯誤訊息與上一次**完全相同**。同輸入同方法只會同輸出。
- 為了讓方案活下來，開始加第 2 個以上的特例／workaround——方案本身錯了。
- 需要的資訊查了兩種來源都查不到——資訊可能不存在，去確認「是否存在」而不是繼續搜。
- 工具連續回同類錯誤（權限、404、schema 不符）——是環境問題，修環境或繞道，不是重呼叫。

**換路的動作**：停、寫下目前方法為什麼失敗（一句話）、列出至少一個不同機制的替代方案、
再動手。寫不出替代方案 = 升級模型或問使用者。

**正例**：外部 API 連續兩次回 429。→ 換路：改用另一個 API，或降低頻率批次查。
不是立刻重打第三次。

**反例**：測試失敗，把斷言值改成實際輸出讓測試變綠。→ 這不是換路，是把驗收條件
改掉。除非有證據證明測試本身錯，否則永遠修實作不修測試。

## R5. 品質底線怎麼驗

交付前的最低檢查，缺一不交：

- **事實**：每個對外陳述的事實找得到來源（檔案:行號、URL、指令輸出）。找不到來源的句子刪掉或標「未查證」。
- **數字**：外部數據（財務、統計、報價）附來源與資料日期。任何自己「算」出來的數字，重算一次或用另一方法交叉驗證。
- **證據**：R2 的證據要求（程式實跑、檔案 read-back、逐項對照原始要求）全數適用；
  檔案 read-back 要檢查開頭、結尾、章節數。
- **程式額外**：lint／型別檢查若專案有設定就跑。沒有測試框架的專案，留一個最小可跑的檢查（assert 式 demo）。
- **模糊題與品味**（文案語氣、設計美感、策略建議）：這是 rubric 的極限——
  檢查表只能保下限。做法：產出後明白標註「此部分屬品味判斷，建議人工過目」，
  或主動用第二意見（不同 model 評審）。**不要假裝 checklist 能保證品味**。

**正例**：研究報告交付前：每個數字都有「（來源：官方 API，2026-07-04）」，
結論段標註「以下為推論，非事實」。

**反例**：報告寫「業界普遍看好後市成長」沒有數字、沒有來源。
這句話在需要可追溯的環境等於造假。
